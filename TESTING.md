# Verification and release checklist

## Local checks

The generated artifact includes unit and browser tests. Final observed results are recorded in `LOCAL-RESULTS.md`. No live Supabase credentials were supplied, so **live auth, real persistence, and RLS are not verified**.

Re-run after any change:

```sh
npm ci
npm test
npx playwright install chromium
npm run test:e2e
npm run build
```

If a system Chromium is intentionally used in CI, set `CI_CHROMIUM=/path/to/chromium`; otherwise Playwright uses its own installed browser. Browser tests are designed for a clean unconfigured environment and explicitly enter demo mode. Do not run them against a public/customer database.

## Manual authentication gate (your configured project)

- [ ] Sign up with a test email, open confirmation email, and verify the account becomes confirmed.
- [ ] Correct password signs in; incorrect password shows an error without revealing records.
- [ ] Logout returns to login; back/refresh cannot reveal a live workspace after logout.
- [ ] Refresh preserves the intended signed-in session; check the profile identifies the account.
- [ ] Request reset email; open the full link and set a 12+ character password.
- [ ] Old password fails; new password succeeds. Cancel reset signs out.
- [ ] Expired/invalid reset links show a failure and never change a password. Request a fresh link to recover.
- [ ] Repeat email callback flows on deployed HTTPS and Android Chrome.
- [ ] Test disconnected network, expired session, and Supabase error/rate-limit feedback. No local fallback saves should occur.

## Manual data and ownership gate

Create two confirmed **test** accounts A and B. Use separate browser profiles or private windows.

- [ ] A adds a lead; creation date is generated by PostgreSQL. Refresh and verify it persists.
- [ ] Edit each field and each status; counts update and edits survive refresh.
- [ ] Verify all 4 status counts and Total, search and filter combinations, and empty results.
- [ ] Cancel deletion and confirm the record remains; confirm deletion and refresh to verify removal.
- [ ] B cannot list, update or delete A's lead by its known UUID via authenticated API requests.
- [ ] B cannot insert with A's `user_id` or reassign its own lead to A.
- [ ] Requests without a signed-in JWT cannot read or write leads.
- [ ] Demo mode makes **no `leads` table requests** and never changes real counts or records.
- [ ] Sign out and sign into another account: no previous account's leads remain visible.
- [ ] Account deletion cascades to that account's test leads (perform only on disposable accounts).

### Automated live CRUD + RLS probe

After applying the migration, create and confirm two distinct disposable test accounts. Set these shell environment variables locally (do **not** prefix them with `VITE_`, do not commit values, do not include a service key):

```text
SUPABASE_URL
SUPABASE_PUBLISHABLE_KEY
TEST_A_EMAIL
TEST_A_PASSWORD
TEST_B_EMAIL
TEST_B_PASSWORD
```

Then run:

```sh
node scripts/test-live.mjs
```

The script signs in both users with the **public** client, creates one clearly named test row owned by A, verifies own CRUD, B's denied cross-account requests, immutable ownership, and anonymous denial; then cleans up its known test UUID. It never bulk deletes data. It does not test signup emails, reset delivery, or UI auth; those remain manual release gates. If a test fails, inspect cleanup and remove any remaining `RLS integration test` row through test account A before rerunning.

## Accessibility, responsive and operational gate

- [ ] Real Android Chrome at approximately 360–430px, landscape, keyboard open, and 200% zoom.
- [ ] Desktop keyboard-only navigation, visible focus, skip link, dialog focus containment/Escape and focus restoration, profile menu, mobile drawer open/close.
- [ ] Screen-reader labels, error announcements, status notifications, contrast in both themes.
- [ ] Confirm long names, long emails, blank optional fields and maximum note length do not break layout.
- [ ] Offline failures and slow requests show usable feedback; double submission is disabled.
- [ ] Check dependencies (`npm audit`) and assess/remediate findings before a public release.
- [ ] Confirm environment config and redirect allowlists match production, not local development.
- [ ] Review Supabase free-plan limits, email sender restrictions, backup/restore needs, and privacy obligations before storing customer data.

## Known scope limits

All leads are loaded for client-side search and counts. There is no server pagination UI, realtime collaboration, conflict resolution, audit history, MFA UI, or automated backup facility. Native dialog accessibility and viewport browser tests are a start, not a full accessibility audit or physical-device certification.
